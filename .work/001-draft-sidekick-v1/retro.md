# Retro — 001-draft-sidekick-v1

## Run summary

- **Route/size:** feature / large. 11 phases run (`sizing → spec → design → develop → spec_review → code_review → qa → docs → release → retro`), all inside one day (2026-08-23T02:17Z → 13:52Z).
- **Human gates:** 2 approvals (spec 02:45Z, design 03:04Z). Everything after design approval ran auto to merge, as designed.
- **Develop:** 15 design tasks, `mode: per-task`, landed in **10 commits** (`e46b981..ddcf4c8`); three commits carry 2–3 tasks each (`0968213` T2+T3, `7165086` T4+T5+T9, `45e7943` T12+T13+T14).
- **Gates:** `spec_review` fail → repair → pass; `code_review` fail → repair → pass; `qa` pass first try. `repair_passes: {spec_review: 1, code_review: 1}` — neither hit the max of 2.
- **Blocking issues found by gates:** 2 (spec_review: AC-50 unreachable K/DST fallback, AC-27 label-vs-settings) + 4 (code_review: B1 NUL separators, B2 no error boundary, B3 unconstructed fetch timeout, B4 prototype-shaped ids). All 6 repaired in 2 commits (`5e25747`, `ed36cd7`). 16 non-blocking observations (N1–N16) + 3 QA findings carried to backlog.
- **Test growth across the run:** 634 → 655 (spec repair) → 671 (code repair); lint/typecheck/build green at every gate.
- **Circuit breaker:** `subagent_calls: 31` against the default cap of **30** — the breaker tripped at the retro boundary and the human raised the cap 30→40 (`.village/constitution.md:21`) so the retro could run. ~4 of the 31 spawns were pure infrastructure loss (`dev-notes-T7.md:7`, `dev-notes-repairs.md:166-167`).
- **Post-release:** `b9fd5d6` (three UX changes from the first real-user session) committed direct to `main`, outside the pipeline.
- **Live-ops:** one real-user session, recorded in `live-ops-notes.md` — 4 environment incidents, 4 new Sleeper platform facts, 4 product-feedback items. It is the only evidence in this run from actual use, and it found things no gate did.

**Verdict shape:** the pipeline shipped a large feature correctly and its checkers were genuinely load-bearing. The mistakes below are concentrated in (a) claims asserted without verification at the design phase, (b) specification defects nothing was chartered to catch, (c) infrastructure the framework does not protect against, and (d) whole categories of behavior — a dead backend, a live draft room, a user's perception — that no phase owned.

## Mistakes

### M1: design.md asserted live-verifiable external facts as verified; four were wrong, all caught downstream by developers

- **evidence** — four claims in `design.md`, each contradicted by a developer running the real thing:
  1. `design.md:307` — nflverse `player_stats.csv` is "all seasons 1999–present combined, 33MB". The file exists and is 33MB, but the whole release was last published **2025-05-07** and its newest season is **2024**; prepping a 2026 draft from it would present a two-year-old log as "most recent", silently, because the file loads fine (`dev-notes-T9.md` §"Live verification", item 1). The live path is the `stats_player` release (`stats_player_week_<season>.csv`), which also changed column names (`team` not `recent_team`, `passing_interceptions` not `interceptions`).
  2. `design.md:15` and `:214` — match DST "against Sleeper's team-defense pseudo-players (position `DST`)". The live dump spells it `DEF`, and the roster slot key is `slots_def`, not `slots_dst` (`dev-notes-T2.md`, live re-verification table; `dev-notes-T3.md:58`).
  3. `design.md:366` (§T15) — build a **mock**-draft fixture "including at least one traded pick". Sleeper cannot express that object: a mock has `league_id: null` and therefore no `slot_to_roster_id`, which is how traded picks resolve. Forced a two-bundle fixture redesign (`dev-notes-T15.md` §1).
  4. `design.md:270` (§T7) — the AC-47 saturation check reads `remainingPicksInWindowIncludingThis`. Read literally this fires for every seat two rounds in, so no simulated pick ever consumes a skill player and **every survival percentage is 100%** (`dev-notes-T7.md` §4). The developer overrode it in the PRD's favour.
  The instructive contrast: the one uncertainty the architect explicitly labelled — `design.md:195` "**Verify at implementation time, don't assume**" on the scoring-settings source — was probed by T2 before any code and got a correct, stronger answer. Meanwhile `design.md:7` says "Verified live during this design pass" of the nflverse URLs; the verification confirmed *existence*, never *currency*, which is the property that mattered.
- **root cause** — `architect.md:15` requires investigating "the real code" and says nothing about external contracts, and nothing in the template forces the architect to separate what it probed from what it inferred. So `design.md` reads at uniform confidence and a fresh-context developer cannot tell which sentences to re-check. Three of the four were cheap facts one `curl` would have settled; the fourth (§T7) was a reasoning error the architect could have caught by working one example. Cost: four developer-side rediscoveries, one fixture redesign, and one wrong structural decision (33MB combined file vs per-season downloads) that survived into the design's own tradeoff reasoning.
- **proposed fixes**
  1. **Require a Verified/Assumed ledger in `design.md`** (recommended) — every claim about an external contract (URL, payload field, enum spelling, release currency, platform capability) gets a row: the claim, `VERIFIED <probe command> <date>` or `ASSUMED`. `ASSUMED` rows inherit a mandatory "probe before coding, report contradictions in dev-notes" note in the consuming task block; the spec-reviewer treats an unlabelled external claim as a design defect. Tradeoff: lengthens design.md and the design phase, and the architect must actually run probes — it has `Bash`, and one of these probes was a HEAD request.
  2. **Move external verification to a pre-design contract-probe task** — design.md forbidden from asserting external shapes at all; a T0 developer probes and writes a contract file the architect then designs against. Tradeoff: clean separation, but adds a spawn and a round-trip, and it starves the architect of exactly the facts its structural decisions depend on (per-season vs combined was a design-time call).
  3. **Push it entirely to the developer** — a rule that every external claim in a task block is re-probed before coding. Tradeoff: free, and it is effectively what saved this run — but it worked only because these developers were diligent, and it leaves the design's own decisions built on unverified premises.

### M2: AC-55 shipped a mathematically dead branch; the developer, not the spec or any gate, caught it

- **evidence** — `spec.md:96` (AC-55) transcribes `prd/draft-sidekick/prd.md` FR-10 bullet 2 essentially verbatim: plan score = rank of the best available at the now-position + expected rank of the best available at the next-position. Read literally, `score(now, next) = f(now) + g(next)` is separable, so `argmin` factorises and the winning plan's now-position is always `argmin f` — the plain best-available-at-a-needed-position pick. Consequences, all in the primary sources: FR-9's **plan/survival** reason ("the winning plan moved the highlight off the overall top-ECR candidate") is unreachable for every possible survivor matrix; FR-10's own headline ("optimizes the user's next two picks jointly") is false of its own formula; AC-56 degenerates to a per-row rule. Caught at **develop** time by T8, which flagged it to the orchestrator as a deliberate departure rather than shipping it silently (`dev-notes-T8.md` §1, "Read literally, AC-55 makes FR-10 a no-op on the highlight"), and fixed by excluding the `term1` player from the `term2` lookup only when now-position == next-position (cross-position plans bit-identical). `spec_review` then re-derived the argument independently and accepted it as a **recorded spec defect** (`review-spec.md` @ `5e25747`, ruling 1 and defect list item (a)). Two sibling spec defects were recorded the same way: AC-36 vs AC-40 never says which scopes derivation and which scopes display (ruling 3), and **no AC covers the `recomputing` flag clearing after a content-free re-ingest** (ruling 5) — that third one then surfaced in QA (`qa.md` non-blocking #1) and again live (`live-ops-notes.md` #15).
- **root cause** — `product-manager.md:17` requires acceptance criteria be *machine-checkable*; nothing requires them to be *non-vacuous*. No phase is chartered to check that a stated algorithm can produce all of its own stated outcomes, and `spec_review` runs **after** develop (`schemas.md` route table), so the earliest structurally possible catch is a developer already writing the code — three phases and a human approval gate downstream of where the defect entered. The defect actually originates in the PRD, which `.village/constitution.md:13` declares law; the spec's job as written is faithful transcription, so a defective PRD passes through untouched. **Residual risk today:** the code deliberately diverges from AC-55 and PRD FR-10, and both documents still state the dead formula — a future maintainer "fixing" the divergence would silently re-kill FR-10.
- **proposed fixes**
  1. **Add a derivation-check duty to the spec phase** (recommended) — for every AC stating a formula, ranking rule, or precedence order, `spec.md` must record a worked example showing each named outcome is reachable, and one example per branch where the AC names mutually exclusive branches. An AC whose branch cannot be exhibited is a spec bug to fix or escalate *before* human gate 1. Tradeoff: real work for the PM agent on math-heavy specs, and longer specs — but this exact check catches AC-55, exercises AC-51's four-way reason precedence, and would have exposed the missing recomputing-clear criterion as a branch with no AC.
  2. **Insert a pre-develop static spec review** — a gate between spec approval and design where the spec-reviewer reads the ACs adversarially against each other with no code. Tradeoff: catches the whole class before any code exists, but adds a gate and a spawn to every feature and duplicates a reviewer that already exists post-develop.
  3. **Formalize the escape hatch that actually worked** — keep the flow, but require the orchestrator to route every dev-notes-flagged spec defect back into the PRD/spec as an *edit*, not merely a record. Tradeoff: cheapest, and honest about where these really get caught; leaves the human's approved artifact wrong and does nothing about detection latency.
- **target files** — `/Users/willyu/village/.claude/agents/product-manager.md`, `/Users/willyu/village/.claude/skills/village/assets/templates/spec.md`, `/Users/willyu/village/.claude/agents/spec-reviewer.md`; and in-repo, the still-wrong text at `prd/draft-sidekick/prd.md` FR-10 bullet 2 and `.work/001-draft-sidekick-v1/spec.md:96`

### M3: four spawns lost to infrastructure, and recovery depended on uncommitted tree state the orchestrator was itself churning

- **evidence** — `dev-notes-T7.md:7`: "This task was resumed. A prior attempt was terminated mid-task by an infrastructure error." `dev-notes-repairs.md:166-167`: code_review repair "ran three times; only infrastructure ended the first two" — attempt 1 landed B1 and wrote 15 red tests before a **stream watchdog** killed it, attempt 2 hit a **session limit** having changed nothing, attempt 3 inherited a tree holding a fix plus failing tests with no implementations behind them. `live-ops-notes.md` #13 confirms two infra-killed developer spawns burned ~3 breaker slots. Both recoveries worked *because uncommitted work survived in the working tree* — and `live-ops-notes.md` #1 records the orchestrator running a `git stash/checkout` that killed `tsx watch` mid-draft, i.e. the same class of command that would have destroyed exactly that unprotected work. Commit granularity widened the blast radius: 15 design tasks in 10 commits, with `7165086` carrying T4+T5+T9 (and T5 `depends_on: [T3, T4]`, so not even parallel-safe) and `45e7943` carrying T12+T13+T14.
- **root cause** — `developer.md:12-21` mandates a two-commit rhythm per task, but nothing in `SKILL.md`'s spawn protocol or branch model (`SKILL.md:63-67`, `106-109`) requires a spawn's work to be committed before the next spawn or the next orchestrator git operation. The resume rule (`SKILL.md:40`) keys on **artifact existence**, not committed code — so partial implementation is protected by nothing but luck, and nothing forbids the orchestrator from mutating git state while a maker or a watcher is live.
- **proposed fixes**
  1. **Per-spawn commit, and orchestrator git-hygiene rule** (recommended) — each developer spawn ends with its own commit(s), never merged across design tasks; the orchestrator's only git writes are branch creation, commit, and merge, and it never runs `stash`/`checkout`/`reset` on a tree with a running process or a live spawn. Tradeoff: a 15-task feature grows to ~30 commits and the orchestrator must verify a commit landed per spawn; buys bisectability and caps any kill at one task's loss.
  2. **WIP checkpoint commits on every green suite run**, with the resume rule reading `git log` instead of artifact existence. Tradeoff: survives a kill at any point, but produces noisy history needing a squash and erodes the test-first commit-order guarantee `developer.md:12` is built on.
  3. **Add an explicit resume contract to `developer.md`** — on spawn, detect and audit inherited uncommitted work against the verdict before writing anything (precisely what attempt 3 did unprompted, `dev-notes-repairs.md` §"Inherited tests"). Tradeoff: free and demonstrably effective, but it protects nothing — it only makes loss survivable when the tree happens to survive.

### M4: the local run environment had four silent failure modes; no phase owned them, and the worst one was read by the user as an engine bug

- **evidence** — `live-ops-notes.md` #1–#4: the dev server was tied to the harness preview pane and **died when the pane closed**; with the backend down, `GET /api/*` returns `index.html` with **HTTP 200** while POSTs 404 — "fake healthy", costing several minutes of misdiagnosis; Vite bound **IPv6-only** (`[::1]:5173`, `127.0.0.1` refused), documented nowhere; and the frontend **held the dead session's last frame** with a reconnect banner easy to miss, so the user saw a stale recommendation (the "Gibbs" incident) and read it as an engine defect. The gap is precise: `qa.md` drove `/api/config` *through* the proxy with the server up (line 22) and hammered server-side failure — malformed payloads, `kill -9` cold reattach, three injected faults, FantasyPros 503 — but never once asked what the **frontend** does when the server process is simply gone. In-repo, `packages/web/vite.config.ts` configures the `/api` + `/events` proxy with no error handler and no `server.host`; `README.md:51-59`'s troubleshooting covers degraded sync, no-rankings mode, and two-drafts-at-once, none of these four.
- **root cause** — every degrade-path AC in the spec (AC-16..AC-21, AC-28, AC-48) is about the app's behavior against **Sleeper**. The app's behavior against **itself** — its own backend absent — is nowhere in the spec, so `qa.md`'s remit ("take the acceptance criteria from `spec.md`", `qa.md:21`) structurally excludes it. A failure mode nobody specified is a failure mode nobody tested, and the constitution's conventions are checked against the diff (`code-reviewer.md:20`), which cannot see a missing behavior.
- **proposed fixes**
  1. **Operator-surface clause in the spec template + a process-death drill in qa** (recommended) — any task shipping a runnable local process must carry ACs for (a) what the frontend shows when its backend is unreachable, and (b) the documented bind address/port and a liveness check; `qa` must drive at least one process-death drill *from the UI*, not only from the server. Pair with a backlog task for the concrete repo fixes: a Vite proxy error handler returning 502 rather than falling through to the SPA shell, `server.host` pinned, a frontend guard that treats `text/html` from `/api/*` as a dead backend, hard-dim + full-screen banner on stream close, and README troubleshooting entries for all four. Tradeoff: widens every feature's AC set with infrastructure concerns the PRD does not care about — the counter is that this is the very first class the real user hit.
  2. **Put it in the constitution as a project convention** — "a local web app must fail visibly: a dead backend must be distinguishable from a healthy one in ≤1 interaction" — and let checkers cite it. Tradeoff: one place, applies to every future task; but conventions are enforced against the diff, so an *absent* behavior slips through.
  3. **Framework unchanged; file the four repo fixes as backlog tasks.** Tradeoff: fixes the instances, guarantees the class recurs on the next runnable surface.

### M5: the out-of-band validation protocol the pipeline handed off was unrunnable as written, and the docs made it worse

- **evidence** — PRD SC-3/SC-4 define the readiness checklist as a **post-draft** record ("recorded after every mock and real draft"). `live-ops-notes.md` #5 found that Sleeper **purges a mock the instant the human leaves the room — even mid-draft** (404 on both draft and picks), so the data those checklists describe is gone before they can be filled in; SC-3/SC-4 must be captured live. The pipeline already held the weaker version of this fact — `spec.md:131` states "mock data is purged server-side once the draft ends" — and drew no consequence for its own validation design. Then `README.md:44-49` ("Mock-rehearsal workflow") tells the user to "join the mock on Sleeper itself first … then paste its URL/ID into Sidekick as usual" and says nothing about the clock: `live-ops-notes.md` #7 records that **bots plus a 90 s autopick blitz an entire draft if the human idles**, and two mocks completed on autopilot while ops incidents were being fixed — rehearsal attempts spent for nothing, against a PRD gate that demands ≥3 full rehearsals. Conversely `live-ops-notes.md` #6 resolved a standing PRD residual (AS-1: does a solo mock's `draft_order` carry the human's `user_id`? yes, verified `{user_id: 8}`) in a single live check that no pipeline phase was empowered to make.
- **root cause** — the pipeline correctly declared live-mock validation out of scope (`spec.md:17`, restated in `changelog.md` §"Validation status") but treated "out of scope" as "not my problem" rather than "produce the runbook and the open-question list for the human who must do it". The `docs` phase wrote the workflow from the PRD's prose, not from any live rehearsal, so it inherited the PRD's leisurely framing — and `qa` had already discovered the adjacent blocker (a joinable live mock needs account sign-in, out of bounds for the agent, `qa.md` line 25) without that discovery changing the handoff.
- **proposed fixes**
  1. **Make the validation handoff a required docs deliverable** (recommended) — when a spec carves out live-judgment validation, `docs` must produce a step-ordered rehearsal runbook that states the platform's timing constraints (attach and be ready *before* the room fills; the draft waits for no one), names the data that must be captured **live** because it is destroyed on exit, and lists the PRD residuals a rehearsal is expected to resolve. Tradeoff: the tech-writer is documenting a process it cannot run, so the runbook is only as good as the research artifacts — but "capture live, the room is destroyed on exit" was derivable from `spec.md:131` plus one probe.
  2. **Add a `rehearsal` phase to the feature route** between release and retro, output = runbook + whatever the agent can verify against the live platform without an account. Tradeoff: makes the gap first-class, but the agent structurally cannot sign in, so the phase can never close and would sit `blocked_on_human` by construction.
  3. **Leave the framework; fix the README as a backlog task.** Tradeoff: cheapest; the class recurs on the next feature whose validation is out-of-band.

Tradeoff: fixes this instance; the class ("shipped to spec, felt wrong") recurs whenever a spec is silent on legibility.

### M7: the circuit breaker was mis-sized and its accounting is incomplete, so the pipeline's own learning phase was the first casualty

- **evidence** — `status.yaml` records `subagent_calls: 31` against the framework default cap of 30 (`SKILL.md:39`), and `.village/constitution.md:21` now carries `circuit_breaker_cap: 40` with the comment "raised 30→40 on task 001 by user request, 2026-08-23, to run retro/improvement". The breaker therefore tripped exactly at the boundary of `retro` + `improvement` — the two phases whose entire purpose is to make the framework better — and required human intervention for the pipeline to learn anything from a run it had already completed. The arithmetic was never survivable: 15 design tasks in `per-task` mode + 3 fixed pre-develop phases + 5 checker spawns (2 spec_review, 2 code_review, 1 qa) + 4 repair-developer spawns + docs + retro is ~30 before a single infra retry, and **~4 of the 31 were pure infrastructure loss** (`dev-notes-T7.md:7`; `dev-notes-repairs.md:166-167` — attempts 1 and 2 of the code repair), a ~13% tax the cap does not budget for. Separately, `live-ops-notes.md` #14 records the **code-reviewer spawning its own background sweep agent** whose completion notification arrived *after* the gate verdict, forcing the orchestrator to classify an un-dispatched return; that spawn was never counted (the orchestrator increments only its own dispatches, `SKILL.md:41`) and is not even granted by that agent's own affordances (`code-reviewer.md:4` lists Read/Glob/Grep/Bash/Write, no `Agent`). `developer.md:27` permits utility subagents, also uncounted. The sweep's findings were good — dead exports, duplicate helpers, hardcoded display thresholds, `postDetach` error handling — and had no home in any artifact, so they were hand-carried to the backlog.
- **root cause** — a flat constant guards a variable-size pipeline: the cap is set in the constitution before the design exists, while the actual spawn count is a function of the design's task count times the repair rounds. And `subagent_calls` measures orchestrator dispatches, not agents that ran, so the number the breaker fires on is not the number it claims to be — the breaker cannot see maker or checker fan-out at all.
- **proposed fixes**
  1. **Derive the cap from the design; exempt the tail; forbid checker fan-out** (recommended) — at design approval the orchestrator computes `cap = fixed_phases + design_task_count + gates × (1 + max_repair_rounds) + 20% infra allowance`, writes it into `status.yaml`, and the constitution's `circuit_breaker_cap` becomes a *ceiling* on that arithmetic rather than the number itself. Exempt `docs`/`release`/`retro`/`improvement` from the breaker — they are bounded and they are where the pipeline learns. State explicitly in the checker agent files that a checker never spawns (its verdict must rest on evidence it derived itself), and require makers to declare utility spawns in dev-notes so fan-out is at least visible. Tradeoff: more orchestrator arithmetic, and the human loses a single eyeballable number; buys a breaker that fires on runaway loops instead of on large-but-healthy features.
  2. **Keep a flat cap, raise the default, and count only productive spawns** — an infra-killed spawn that produced no artifact does not increment. Tradeoff: simple and it directly refunds the 13% infra tax; but "productive" needs a rule, and it removes protection against a spawn that dies in a loop.
  3. **Keep everything; make the trip non-fatal for tail phases only.** Tradeoff: two-line change that unblocks the retro forever; does nothing about the accounting gap or about a large feature legitimately needing 40 mid-run.
- **target files** — `/Users/willyu/village/.claude/skills/village/SKILL.md` (breaker, spawn protocol, phase dispatch), `/Users/willyu/village/.claude/skills/village/references/schemas.md` (`status.yaml` fields), `/Users/willyu/village/.claude/agents/code-reviewer.md`, `spec-reviewer.md`, `qa.md`, `developer.md`

## What worked (keep, don't touch)

- **Evidence-gated checkers with mutation testing.** `code_review`'s second pass did not accept a green suite as proof a guard exists: it reverted each repair and confirmed the covering suite went red — reproducing B2's exact crash trace and B4's exact 500 — and reconstructed the pre-repair `montecarlo.ts` byte-for-byte to prove the seed had not moved (`review-code.md` §B1, §B2, §B4). It also probed the process guards in a **real child process on Node 26** with unguarded controls, because asserting "still alive" inside the test runner would have asserted nothing. This is the single highest-value behavior in the run.
- **Discriminating fixtures with internal controls.** `spec_review`'s re-check did not just confirm the new AC-50 test passes; it found the sibling case that differs *only* in the ADP feed and produces the opposite result, proving the assertion could not have passed pre-repair (`review-spec.md` §"Sensitivity is established by an internal control").
- **Resume-from-partial-state.** Both infra kills were recovered without redoing sound work, and attempt 3 audited all 15 inherited red tests against the verdict before writing a line (`dev-notes-repairs.md` §"Inherited tests"). Worth hardening (M3), not replacing.
- **Stateless full-refetch as a testable architecture.** `kill -9` mid-draft then a cold attach produced a **byte-identical** 43,610-byte snapshot versus a live-watched process (`qa.md` §"Kill/restart mid-draft"). The constitution's "never incremental diffs" rule turned recovery into a property that can be asserted rather than hoped for.
- **Developers flagging spec/design defects instead of silently complying.** T7 (`remainingPicks`), T8 (AC-55), T9 (nflverse release), T15 (mock+trade fixture) each argued the departure in dev-notes with the primary sources cited. Both of `spec_review`'s own blocking issues had been forward-referenced in dev-notes before the gate found them. The pipeline's best defect detector was a maker with permission to disagree.
- **Configurability as a constitution rule.** All 27 🔶 AS-N thresholds live in one parameters module with a `config.local.json.example` that the reviewer proved actually loads (`review-code.md` §B3) — so live tuning after a rehearsal needs no code change.
- **The orchestrator writing `live-ops-notes.md`.** An unschematized artifact that turned out to be the highest-signal input to this retro. Promote it to a real artifact (M8, option 1).
